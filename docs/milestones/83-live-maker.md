## First implementation increment

The new `sdk/src/maker-live-snapshot.mjs` observes both complete linked books and canonical maker balance from a single batched context, derives page and later sidecar PDAs, verifies market-bound configured head sidecars, validates freshness and pinned genesis, checks cross-side sequences and minimum locked collateral, and returns observation-only state. The head BID sidecar uses the protocol's existing 16-byte binding; require a configured full key rather than pretending the tag is a full PDA. Unused detached canonical suffix accounts are not treated as live depth. No signing or sending code is added. Custody/vault/mint and aggregate-floor authentication, executable admission, and journal integration remain subsequent work. The new tests require fresh CI.

## Second implementation increment: aggregate collateral observation

Custody identity discovery is followed by a single context batch of both books, maker balance, canonical custody, passive pool, lazy reserve, SPL vaults and mints. Custody identities and decimals must remain unchanged between reads. The snapshot authenticates program ownership, canonical PDA bumps, mint decimals, vault authority and initialized token accounts, checks pinned reserve genesis, and requires the combined custody + frozen claims/fees + passive principal/fees vault floor. It returns the M82 guard account roles when enabled. Absent canonical reserve accounts are accepted only as null or empty system accounts; guarded markets require a passive pool. The maker's own free and locked balances cannot exceed custody totals. All observations remain read-only; an RPC source is trusted and these checks are not proof of all makers' individual balances or authorization to submit. Tests cover altered custody, frozen vault, mint mismatch, missing pool, reserve domain, deficits and overflow-sensitive accounting. Fresh CI and review are required.

## Third implementation increment: read-only quote and risk planning

Nominal maker balances may include frozen but unclaimed lazy fills. The observation bound now includes authenticated global pending debits; it never credits those debits to free inventory. Until maker-specific claim reconciliation is implemented, a nonzero market-wide pending debit or credit blocks advisory mutation plans. This deliberately conservative availability tradeoff is separate from vault solvency. The new planner reads a fresh authenticated snapshot, converts integer lot/price targets, matches resting orders one-to-one, and separates cancellation from placement. It checks operator opt-in, kill switch, pending journal status, slot lag, order/transaction/retry counts, gross quote exposure, worst-case base exposure and marked inventory drawdown against explicitly supplied limits. Rate counters and equity baseline are trusted operator inputs at this stage, not durable authenticated execution state. Loss calculation is a spot-marked quote-atom inventory drawdown, not realized P&L; deposits and withdrawals require an updated reconciled baseline. No signer or send path is exposed. Placement is constrained to the current supported page-zero ABI and current free collateral; multi-page cancellations need a separate authenticated instruction integration. Fresh CI required.

## Fourth implementation increment: durable single-intent preparation

A new disk-backed session pins program, market, maker, head-sidecar and genesis identities, risk limits and operator-approved equity baseline. Under the existing exclusive maker lock it reserves only one advisory action, derives the first canonical SDK instruction from a fresh snapshot, compiles a maker-paid unsigned v0 message with a context-bound RPC blockhash and persists that exact message plus risk counters before exposing it for external signing. A second reservation is blocked until independent reconciliation is implemented. The preparation step accepts only the reserved message with one nonzero signature, revalidates slot/blockhash freshness, simulates the exact signed wire with signature verification, and persists the existing atomic v2 journal and wire identity. Recovery can inspect signature status but cannot broadcast, release, or retry an intent. Missing/corrupt state, stale locks, interrupted .pending files, unverified finality and inconsistent journal identities block progress. The baseline and limits remain explicit trusted operator configuration; counters are durable reservations, not measured submission counts. There is intentionally no automatic release, retry, rolling execution loop or unattended trading. The first signed funded sandbox lifecycle is a subsequent increment; CI and review required.

## Fifth implementation increment: explicit single-attempt sandbox broadcast

The session now supports an opt-in, one-shot raw transaction broadcast only to a trusted HTTP literal loopback RPC with explicit port (127.0.0.1 or ::1); public RPC endpoints remain disabled. Re-authenticate both books and aggregate custody, re-evaluate the durable risk policy using reserved counters, regenerate the exact original message, re-simulate signature-verified bytes, and re-check slot, height, genesis and kill switch before sending. Journal and session are durably marked submitted before the network call; SDK RPC retries are disabled and an ambiguous response does not permit a second broadcast. Recovery verifies historical finalized status and a matching full v0 transaction receipt (signature, serialized message, slot, success) before recording finality. The session remains blocked after finality, pending independent post-state reconciliation. Pre-submit maker inventory, owned orders, sequence, custody and vault amounts are persisted for that next increment. Mock-RPC tests use real externally signed web3 messages; no real funded transaction evidence yet. A loopback endpoint can proxy another cluster, so operator must separately attest isolated local genesis and test-wallet custody. No automatic retry, retirement, public devnet or mainnet sending, or unattended operation is enabled. Fresh CI and review required.
